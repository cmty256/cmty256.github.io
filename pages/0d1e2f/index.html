Gradle依赖管理

# Gradle 依赖管理

依赖管理是构建工具的核心能力。Gradle 的依赖管理比 Maven 更细粒度、更灵活，本文从配置项、Version Catalog、排除依赖、BOM 等方面全面讲解。

# 依赖配置项（Configuration）

# 与 Maven Scope 的对比

Maven 只有 6 种 scope（compile / provided / runtime / test / system / import），而 Gradle 提供了更细粒度的配置项：

Gradle 配置项 说明 编译 运行 测试 打包 Maven 对应
implementation 主依赖，不暴露给下游 ✅ ✅ ✅ ✅ compile
api 主依赖，暴露给下游 ✅ ✅ ✅ ✅ compile（传递）
compileOnly 仅编译时需要 ✅ ❌ ✅ ❌ provided
runtimeOnly 仅运行时需要 ❌ ✅ ✅ ✅ runtime
testImplementation 测试编译和运行 ❌ ❌ ✅ ❌ test
testCompileOnly 仅测试编译 ❌ ❌ ✅ ❌ -
testRuntimeOnly 仅测试运行 ❌ ❌ ✅ ❌ -
annotationProcessor 注解处理器（编译期） - - - ❌ -
developmentOnly 开发时需要（DevTools） - ✅ - ❌ -

# implementation vs api（核心区别）

这是从 Maven 转 Gradle 最需要理解的概念：

  • implementation：依赖不会泄漏到下游模块的编译 classpath。下游模块看不到这个依赖的 API。
  • api：依赖会泄漏到下游模块的编译 classpath。下游模块可以直接使用这个依赖的类。
模块 A → implementation(模块B) → 模块B的依赖C
模块 A 看不到 C 的类（编译时）

模块 A → api(模块B) → 模块B的依赖C
模块 A 能看到 C 的类（编译时）
1
2
3
4
5

选择原则：

场景 选择
依赖只在模块内部使用 implementation（推荐，默认选择）
依赖的类型出现在模块的公开 API 方法签名中 api

为什么默认用 implementation？ 因为它能让 Gradle 更好地优化构建。当 implementation 依赖变化时，只有当前模块需要重新编译，下游模块不受影响。而 api 依赖变化时，所有下游模块都要重新编译。

# 实际项目示例

interview-guide 项目的依赖配置：

dependencies {
    // implementation：主依赖，不暴露
    implementation 'org.springframework.boot:spring-boot-starter-webmvc'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'

    // runtimeOnly：运行时才需要（数据库驱动）
    runtimeOnly 'org.postgresql:postgresql'

    // compileOnly + annotationProcessor：Lombok
    compileOnly libs.lombok
    annotationProcessor libs.lombok

    // testImplementation：测试依赖
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testRuntimeOnly 'com.h2database:h2'
}

# Version Catalog（版本目录）

Version Catalog 是 Gradle 7+ 引入的依赖版本集中管理机制，用 TOML 文件统一声明所有依赖的版本，替代在 build.gradle 中散落的版本号。

类似 Maven 的 <dependencyManagement> + BOM，但更直观、更易维护。

# 文件位置

项目根目录/
└── gradle/
    └── libs.versions.toml   # Version Catalog 文件
1
2
3

文件名 libs 是默认的 Catalog 名称，在 build.gradle 中通过 libs 引用。Gradle 会自动识别 gradle/ 目录下的 *.versions.toml 文件。

# 文件结构

Version Catalog 文件包含四个部分：

# 1. 版本号定义
[versions]
spring-boot = "4.1.0"
lombok = "1.18.46"

# 2. 依赖库定义
[libraries]
lombok = { module = "org.projectlombok:lombok", version.ref = "lombok" }
tika-core = { module = "org.apache.tika:tika-core", version.ref = "tika" }

# 3. 插件定义
[plugins]
spring-boot = { id = "org.springframework.boot", version.ref = "spring-boot" }

# 4. Bundle 定义（一组依赖打包引用）
[bundles]
tika = ["tika-core", "tika-parsers"]

# 命名转换规则

Version Catalog 中的名称在 build.gradle 中引用时，遵循以下转换规则：

TOML 中的名称 引用时的名称 规则
lombok libs.lombok 直接使用
tika-core libs.tika.core 连字符 - 转为 . 分隔
spring-boot libs.spring.boot 连字符 - 转为 . 分隔
junit-jupiter libs.junit.jupiter 连字符 - 转为 . 分隔

版本号引用：libs.versions.springAi.get()，注意 .get() 是必须的（返回 Provider<String>）。

# 版本号引用方式

[versions]
spring-boot = "4.1.0"
springAi = "2.0.0"

[libraries]
# 方式一：version.ref 引用上面定义的版本
spring-boot-starter = { module = "org.springframework.boot:spring-boot-starter", version.ref = "spring-boot" }

# 方式二：直接写死版本
my-lib = { module = "com.example:my-lib", version = "1.0.0" }

# 方式三：不指定版本（由 BOM 或 dependency management 控制）
spring-ai-agent-utils = { module = "org.springaicommunity:spring-ai-agent-utils" }

# BOM / Platform

# 什么是 BOM

BOM（Bill of Materials）是一个特殊的 POM，只声明依赖版本，不实际引入依赖。用于统一管理一组相关依赖的版本。

# Gradle 中的 BOM：platform

Gradle 用 platform() 引入 BOM：

dependencies {
    // 引入 BOM，统一管理版本
    implementation platform('org.springframework.boot:spring-boot-dependencies:4.1.0')

    // 之后引用 BOM 管理的依赖时，无需指定版本
    implementation 'org.springframework.boot:spring-boot-starter-web'
}

# platform vs enforcedPlatform

方式 说明
platform() 软约束，BOM 中的版本可被覆盖
enforcedPlatform() 硬约束，BOM 中的版本不可被覆盖
// 软约束：可以覆盖版本
implementation platform('org.springframework.boot:spring-boot-dependencies:4.1.0')
implementation 'org.postgresql:postgresql:42.7.0'  // 覆盖 BOM 中的版本

// 硬约束：不可覆盖
enforcedPlatform('org.springframework.boot:spring-boot-dependencies:4.1.0')
implementation 'org.postgresql:postgresql'  // 必须使用 BOM 中的版本

# 依赖冲突解决

# Gradle 的默认策略

Gradle 默认选择最高版本的依赖。当多个依赖引入同一库的不同版本时，Gradle 自动选择版本号最大的。

A → C:1.0
B → C:2.0
结果：使用 C:2.0
1
2
3

这与 Maven 的"路径优先"策略不同。Maven 选择层级最浅的版本，Gradle 选择版本号最高的。

# 查看依赖树

# 查看完整依赖树

gradlew dependencies --configuration runtimeClasspath

# 查看依赖 Insight（某个依赖的来源）
gradlew dependencyInsight --dependency org.slf4j:slf4j-api --configuration runtimeClasspath

# 完整依赖配置示例

以下是 interview-guide 项目依赖配置的结构概览：

dependencies {
    // ===== Spring Boot Starters =====
    implementation 'org.springframework.boot:spring-boot-starter-webmvc'
    implementation 'org.springframework.boot:spring-boot-starter-validation'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'

    // ===== 运行时依赖 =====

    // ===== Version Catalog 引用 =====
    implementation libs.tika.core
    implementation libs.tika.parsers
    implementation libs.springdoc
    implementation libs.pinyin4j

    implementation "org.springframework.ai:spring-ai-starter-model-openai:${libs.versions.springAi.get()}"

        exclude group: 'org.slf4j', module: 'slf4j-simple'

    // ===== 注解处理器 =====
    compileOnly libs.lombok

    implementation "org.mapstruct:mapstruct:${libs.versions.mapstruct.get()}"
    annotationProcessor "org.mapstruct:mapstruct-processor:${libs.versions.mapstruct.get()}"

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation libs.junit.jupiter
    testRuntimeOnly 'com.h2database:h2'
}
