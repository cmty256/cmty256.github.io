# AI 智能面试辅助平台

# 项目目录结构

项目采用前后端分离架构，后端基于 Spring Boot 4.1 + Java 25 + Spring AI 2.0，前端基于 React 18 + TypeScript + Vite。后端按"通用能力（common）+ 基础设施（infrastructure）+ 业务模块（modules）"三层组织，业务模块按领域划分。

# 核心功能与技术亮点

以下功能点是本项目最值得学习、可写入简历的核心技术实现，每个都涉及一定的设计深度。

# 1、基于 Redis Stream 的异步任务处理框架

核心类：common/async/AbstractStreamProducer、AbstractStreamConsumer

简历分析、知识库向量化、面试评估等耗时操作统一走 Redis Stream 异步处理，而非同步阻塞调用 LLM。项目用模板方法模式抽象出生产者/消费者基类，各业务只需实现 parsePayload、processBusiness、markCompleted 等钩子方法。

技术亮点：

  • 失败自动重试：消费失败后按 retryCount 重新入队，超过 MAX_RETRY_COUNT 才标记失败，避免因 LLM 偶发抖动导致任务直接报废
  • Pending 消息认领：消费者崩溃后遗留的 Pending 消息会被其他消费者按 PENDING_IDLE_TIMEOUT 认领，防止消息丢失
  • 任务恢复调度：ResumeAnalysisRecoveryScheduler 定时扫描中断状态的任务重新投递，应对应用重启场景
  • Fencing Token 防并发：任务带 attempt 版本号，防止恢复调度器和正常消费链路同时处理同一任务
  • Stream 最大长度限制：STREAM_MAX_LEN 防止 Stream 无限膨胀

简历话术：基于 Redis Stream + 模板方法模式实现异步任务框架，支持失败重试、Pending 消息认领、宕机恢复和 Fencing Token 并发防护，解耦耗时 LLM 调用与接口响应。

# 2、RAG 检索增强问答（多路召回 + 流式输出）

核心类：modules/knowledgebase/service/KnowledgeBaseQueryService

知识库问答不是简单的"向量检索 → 拼 Prompt → 调 LLM"，而是做了完整的检索优化链路。

技术亮点：

  • Query 改写：用 LLM 将用户口语化问题 + 历史对话改写为更适合向量检索的查询，改写失败自动降级为原问题
  • 双路召回融合：改写 Query 和原始 Query 各检索一次，按 Document ID 去重、按分数降序取 TopK，兼顾语义改写收益和原始查询保底
  • 动态检索参数：根据问题长度分档选择 TopK 和相似度阈值（短查询用小 TopK + 高阈值，长查询用大 TopK + 默认阈值），避免一刀切
  • SSE 流式 + 探测窗口归一化：流式输出时先缓冲前 120 字符探测是否为"无结果"模板，命中则立即返回固定文案，未命中则尽快透传，兼顾首包延迟和拒答识别
  • 全链路 Micrometer 埋点：rewrite / retrieve / generate / total 四个阶段分别记录耗时和成功/拒绝/错误状态，可观测性强
  • Prompt 注入防护：系统提示词拼接 ANTI_INJECTION_INSTRUCTION，防止用户构造恶意问题绕过知识库范围

简历话术：实现 RAG 检索增强问答，包含 Query 改写、双路召回融合、动态 TopK/阈值、SSE 流式探测窗口归一化和全链路 Micrometer 指标埋点。

# 3、统一面试评估引擎（分批 + 二分恢复 + 降级兜底）

核心类：common/evaluation/UnifiedEvaluationService

文字面试和语音面试共用同一套评估逻辑，核心难点是：题目多时单次 LLM 调用容易超时或返回格式错误。

技术亮点：

  • 问答组不可拆分：主问题和其追问构成一个 QaGroup，分批时以组为最小单元，保证上下文完整
  • 分批评估：按 evaluationBatchSize 将问答组分批，每批独立调用 LLM 评估，降低单次 Token 消耗和超时风险
  • 二分恢复：某批评估失败时，若组数足够则二分为左右半批各自重试，对失败侧递归下钻；不可再拆时整段加试一次，仍失败才降级。用 extraBudget 限制额外调用次数，防止无限重试
  • 二次汇总：所有批次评估完成后，再调一次 LLM 做全局汇总（综合评语 + 优势 + 改进建议），汇总失败降级为批次结果拼接
  • 索引映射容错：LLM 返回的 questionIndex 可能错位（1-based 偏移、缺失），通过 isConsistentOneBasedShift 检测整批一致偏移并按位置对齐，非法索引只降级该题为 0 分，不影响其他题
  • 显式降级标记：降级分数明确标注"模型评估失败后的系统降级"，不伪装成真实评分

简历话术：设计统一面试评估引擎，支持分批评估、问答组不可拆分、失败二分恢复（带预算控制）、二次汇总和索引映射容错，保证评估结果完整性和可靠性。

# 4、实时语音面试（WebSocket + 虚拟线程 + 句子级并发 TTS）

核心类：modules/voiceinterview/handler/VoiceInterviewWebSocketHandler

语音面试是全项目技术复杂度最高的模块，处理管线：用户音频 → ASR → LLM → TTS → AI 音频。

技术亮点：

  • 虚拟线程执行管线：LLM/TTS/JDBC 等阻塞操作跑在 newVirtualThreadPerTaskExecutor() 上，不阻塞调度线程，充分利用 Java 25 虚拟线程高并发优势
  • 句子级并发 TTS：LLM 流式输出期间，每检测到一个完整句子就并发启动 TTS 合成，用 Semaphore 控制并发数，OrderedTtsChunkEmitter 保证音频按序下发，首包延迟约 200ms
  • 服务端 VAD + 手动提交：ASR 自动断句产生 final segment，但提交给 LLM 由前端手动 submit 控制，避免抢话
  • 回声防护：AI 说话期间及结束后 800ms 冷却期内丢弃麦克风输入，防止扬声器声音被重新录入触发 LLM
  • 上下文压缩：VoiceContextCompressor 对超长对话历史做摘要压缩，控制 LLM Token 消耗
  • 开场白音频预热：@PostConstruct 时预合成开场白音频缓存，首次连接直接播放，避免冷启动延迟
  • ASR 断线重连：ASR 连接异常时自动重连并重试音频块发送，最多重试 2 次
  • 暂停超时检测：@Scheduled 每 30s 检查无活动会话，4:30 发警告，5:00 自动暂停
  • 全链路 Micrometer 埋点：first_token_latency / llm.duration / tts.duration / turn.duration / asr.merge_wait 等指标

简历话术：基于 WebSocket + Java 25 虚拟线程实现实时语音面试，支持句子级并发 TTS（首包 200ms）、服务端 VAD、回声防护、上下文压缩、ASR 断线重连和全链路指标埋点。

# 5、可重复注解的多维度限流（Redis Lua 原子检查）

核心类：common/annotation/RateLimit、common/aspect/RateLimitAspect

技术亮点：

  • 可重复注解：@Repeatable 支持同一方法标注多条限流规则（如 GLOBAL + IP + USER），所有规则在一次 Lua 调用中原子检查和扣减，避免多次 Redis 往返
  • Lua 脚本 + EVALSHA：脚本预加载为 SHA1 缓存，每次用 evalSha 执行；Redis 重启导致 NOSCRIPT 时自动重新加载并重试
  • 多维度 Key 设计：用 {ClassName:MethodName} HashTag 保证同一方法的多维度 Key 落在同一 Redis 槽位，Lua 脚本可跨 Key 原子操作
  • 失败规则定位：Lua 返回负数表示第几条规则触发，切面据此定位并执行对应降级
  • 降级方法支持：限流触发时可调用指定的 fallback 方法（无参或参数一致），而非直接抛异常
  • IP 穿透：依次解析 X-Forwarded-For / X-Real-IP / Proxy-Client-IP 等头，适配反向代理场景

简历话术：基于可重复注解 + Redis Lua 实现多维度（Global/IP/User）原子限流，支持 EVALSHA 缓存、NOSCRIPT 自愈、HashTag 槽位对齐和方法级降级。

# 6、多 LLM Provider 动态管理

核心类：common/ai/LlmProviderRegistry

技术亮点：

  • 运行时切换：Provider 配置存数据库，设置页可动态新增/切换默认聊天模型和向量模型，无需改代码重启
  • ChatClient 缓存：按 providerId 缓存 ChatClient / ChatModel / EmbeddingModel，reload() 清空缓存重建
  • 多类型 Client：getDefaultChatClient（带工具+记忆）、getPlainChatClient（无工具，用于结构化输出）、getVoiceChatClient（带工具+流式 ToolCall，无记忆），按场景选择
  • API Key 加密落盘：ApiKeyEncryptionService 对 API Key 加密存储，运行时解密，配置写到 ~/.interview-guide/
  • Advisor 编排：可配置 SafeGuardAdvisor（敏感词拦截）、MessageChatMemoryAdvisor（对话记忆）、ToolCallingAdvisor（工具调用）、SimpleLoggerAdvisor
  • OpenAI 兼容：通过 ApiPathResolver 适配 DashScope / Kimi / DeepSeek / GLM / LM Studio 等不同 BaseUrl 路径

简历话术：实现多 LLM Provider 动态管理，支持运行时切换、ChatClient 缓存、API Key 加密、按场景编排 Advisor（SafeGuard/Memory/ToolCall），兼容多家 OpenAI 协议模型。

# 7、Skill 驱动智能出题

核心类：modules/interview/skill/InterviewSkillService、resources/skills/

技术亮点：

  • SKILL.md 定义考察范围：每个面试方向一个 SKILL.md + skill.meta.yml，定义知识点、难度分布、参考题库，新增方向只需加目录
  • Tool Calling 集成：interviewSkillsToolCallback 注册为 LLM 工具，LLM 出题时可调用 Skill 资源
  • 历史题目去重：出题时排除该用户已有会话中问过的题目，避免重复考察
  • 10+ 方向覆盖：Java 后端、阿里/字节/腾讯专项、前端、Python、算法、系统设计、测开、AI Agent 等

简历话术：基于 SKILL.md + Spring AI Tool Calling 实现 Skill 驱动智能出题，支持 10+ 面试方向、历史题目去重和参考知识库加载。

# 8、内容哈希去重

核心类：infrastructure/file/FileHashService

上传简历时计算文件内容哈希，命中已分析过的相同简历直接返回历史结果，避免重复消耗 LLM Token。简单但实用的成本优化。

# PGvector 向量功能

虽然镜像已经内置了向量功能，但 PostgreSQL 的设计是“插件按需加载”。按理说你得手动执行 CREATE EXTENSION vector;。

但是！ 如果你用的是 Spring AI，你会发现哪怕不手动输入命令，项目也能跑。这是因为 Spring AI 的 PgVectorStore 已经在底层帮你把脏活累活干了。在 Spring 容器启动时，自动检测并初始化 PostgreSQL 的向量数据库环境。

forcePathStyle(true) 必须开启，否则 SDK 会使用虚拟主机风格（bucket.endpoint）导致 DNS 解析失败
region S3 协议要求，本地部署可设为任意值

# 云端 API vs 本地部署

在开始之前，先了解两种方案的特点，选择适合你的方式：

对比项 阿里云百炼 API (云端) Ollama 本地部署 (本地) 点评
部署难度 零部署，开箱即用 需要安装、配置环境 想快速上线选云端，想折腾底层选本地。
硬件要求 无要求 极高（内存/显存是刚需） 本地跑 7B 模型至少得 16G 内存。
推理性能 极快（专业 GPU 集群） 取决于你的显卡 生产环境的吞吐量云端完胜。
费用成本 按 Token 计费（有免费额度） 完全免费 适合“白嫖”党做本地实验。
数据隐私 数据上传云端 数据 100% 本地化 金融、内网环境建议选本地。
适用场景 生产环境、高质量业务 开发测试、隐私敏感场景 没有银弹，看你的业务痛点在哪。

如果是为了更好的分析效果，且不想因为硬件性能导致系统“假死”，个人强烈建议首选阿里云百炼 API。本地模型虽然香，但对普通开发机来说，处理长文本分析简直是“折磨”。

# .env 文件如何生效

很多人以为 Spring Boot 会自动读取 .env 文件，其实不会。application.yml 里的 ${AI_BAILIAN_API_KEY} 占位符是从环境变量取值，而 Spring Boot 本身不读 .env 文件。

那为什么 ./gradlew :app:bootRun 启动时 .env 能生效？因为 app/build.gradle 的 bootRun task 里手动解析了 .env 并注入为子进程环境变量：

// app/build.gradle
tasks.named('bootRun') {
    def envFile = rootProject.file('.env')
    if (envFile.exists()) {
        envFile.eachLine { line ->
            // 解析 KEY=VALUE，通过 environment key, val 注入
            environment key, val
        }
    }
}

# IDEA 中如何启动

既然 .env 靠 bootRun task 注入，那在 IDEA 里直接点主类的绿色按钮运行，会读不到 .env（因为没走 bootRun）。有三种方式解决：

方案 A（推荐）：用 Gradle 面板跑 bootRun

IDEA 右侧 Gradle 面板 → app → Tasks → application → 双击 bootRun。这走的是 build.gradle 里那段 .env 注入逻辑，和命令行完全等价，绿色按钮也能点。

方案 B：装 EnvFile 插件

IDEA Settings → Plugins → 搜 EnvFile 安装 → Run Configuration 里勾选 Enable EnvFile → Add 选 .env 文件。之后直接运行主类即可，插件自动注入。

方案 C：手动配置环境变量

Run Configuration → Environment variables 旁的图标 → 把 .env 里的 KEY=VALUE 逐条粘贴。变量少时可用，多了麻烦。

注意：方案 B/C 是直接运行主类（不走 bootRun），build.gradle 里那段 .env 注入逻辑不会生效，必须靠插件或手动补。方案 A 最省事。
